Have you ever left your computer and returned to find a window open or activity you don't remember? If you use Windows 11, you can examine some sign-in records without installing third-party software by using the built-in Event Viewer tool. However, a recorded logon session does not automatically mean someone else used the computer.

Quick answer

Open Event Viewer, go to Windows Logs > Security, and look for event 4624 for successful logons, or 4625 for failed attempts. Check the Logon Type, account name, and timestamp before interpreting the results. Some events are generated routinely by Windows services.

What can Windows security logs reveal—and what are their limits?

Security logs may record when logon sessions were created, failed authentication attempts, and workstation lock and unlock events. They can help you identify the account associated with an event and whether a session was local, network-based, or remote.

However, these events cannot establish the real-world identity of the person sitting at the computer, or show everything that person did. The absence of a particular event does not prove that no activity occurred: what gets recorded depends on audit settings and how long logs are retained.

How to check recent sign-ins on Windows 11

Start with the built-in Windows method. You don't need to download any software.

  1. Press Win + R to open the Run dialog.
  2. Type eventvwr.msc, then press Enter.
  3. In the left-hand pane, open Windows Logs and select Security.
  4. In the Actions pane, choose Filter Current Log.
  5. In the Event IDs field, enter 4624 and click OK.
  6. Open an event and review its time, the New Logon section, and the Logon Type.

If you're checking whether something happened while you were away, compare the timestamp with that period, then examine the logon type. Many ordinary system events do not mean someone opened the computer's screen.

Important note

You may need Administrator privileges to read the Security log. Don't treat event 4624 appearing at midnight as evidence of a breach without examining its details.

Key Event IDs for investigating sign-ins

These are useful starting points for most users:

Event IDWhat the event means
4624A successful logon session was created.
4625A logon attempt failed.
4800The workstation was locked, if the relevant auditing is enabled.
4801The workstation was unlocked, if the relevant auditing is enabled.

To filter for several IDs at once, enter 4624,4625,4800,4801 in the Event IDs field. Don't expect every event to appear on every computer; some depend on audit policy.

How to read Logon Type without drawing the wrong conclusion

Within event 4624, find Logon Type. This field describes the kind of session and helps distinguish a person using the computer from a service starting or a network connection.

TypeMeaning
2Interactive: An interactive sign-in to this computer.
3Network: A network logon; by itself, it does not mean someone controlled the screen.
5Service: A session associated with a service being started.
7Unlock: The workstation was unlocked.
10RemoteInteractive: An interactive remote sign-in, such as through Remote Desktop.
11CachedInteractive: A sign-in using locally cached credentials.

If you find Logon Type 5 while you were asleep, a background service may be responsible. An unexpected account and time associated with Logon Type 10 warrant further investigation, but do not independently prove a breach. Likewise, Logon Type 3 may involve access to a network resource without opening the desktop.

How to identify the account that signed in

Open the event under the General or Details tab and review these fields:

Date and Time
The event's timestamp. Compare it with the time you were away.
New Logon > Account Name
The account for which the new session was created.
Account Domain
The computer or domain the account belongs to.
Logon Type
The session type: interactive, network, service, or remote.
Source Network Address
The connection's source address when the authentication mechanism provides it. This field may normally be blank or display -.
Logon ID
An identifier that helps correlate events associated with the same session during a more advanced investigation.
Don't confuse Subject with New Logon

The Subject section typically identifies the account or process that requested the logon session, while New Logon identifies the account for which the session was created. Confusing them can lead to incorrect conclusions.

How to find failed sign-in attempts

Return to Filter Current Log, enter 4625, and open the events you want to investigate. Examine the time, account name, logon type, failure reason, and source information if available.

A failed attempt might result from an incorrectly entered password, a service using outdated credentials, or an unauthorized attempt. Don't assume every attempt involving a PIN or Windows Hello will appear in the same way: the events depend on the authentication method and system configuration.

How to check when the screen was locked or unlocked

You may see event 4800 when the computer is locked and 4801 when it is unlocked. Recording these events depends on the Audit Other Logon/Logoff Events setting, which might not be enabled. Their absence is therefore not evidence that logs were deleted or that a breach occurred.

If you want to reconstruct what happened after you left your desk, compare the timing with events 4624 and 4625, as well as any available lock and unlock events, instead of relying on a single ID.

Check sign-in history with PowerShell

To review up to 50 successful and failed logon events from the last seven days, open Windows PowerShell with Administrator privileges and run:

Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    Id        = 4624, 4625
    StartTime = (Get-Date).AddDays(-7)
} -MaxEvents 50 |
Select-Object TimeCreated, Id, Message |
Format-List

This command is read-only: it does not delete logs or change system settings. Output can be lengthy because Message includes each event's details. If you get Access is denied, check your permissions. If there are no results, that only means no matching events were retrieved for the requested period—not that the computer is necessarily secure or compromised.

Example: a logon event at 2 a.m.

Suppose you haven't used the computer since midnight, but you find an event logged at 2 a.m.:

  1. 4624, type 5: This may be a service starting. Check the account and context; don't automatically attribute it to a person.
  2. 4624, type 2: An interactive session exists. Check the account, who is authorized to use the device, and surrounding events.
  3. 4624, type 10: An interactive remote session exists. If you didn't expect it, investigate the account, source, Remote Desktop settings, and other evidence.

A safe hands-on test

The best way to understand the logs is to compare them with an action you know you performed. Try this on your own computer:

  1. Open Event Viewer > Windows Logs > Security and note the time.
  2. Save your work and press Win + L to lock the screen.
  3. Unlock the computer using your usual method.
  4. Return to the log, click Refresh, and look for events near the time of your test.
  5. Note the Event ID and Logon Type, if available, and compare them with the action you performed.

The events may differ depending on account type, authentication method, and audit policy. There's no need to change security settings merely to complete this exercise.

What to do if you find suspicious activity

If you notice an unfamiliar account, an unexpected remote session, or repeated events you cannot explain, don't use a single log entry to declare the computer compromised. Take these steps:

  1. Document the evidence: Record the event's time and ID, account, and session type. Export the logs if an investigation is needed.
  2. Review accounts: Check which users are authorized to access the computer.
  3. Check remote-access tools: Review Remote Desktop and other remote-control software when relevant.
  4. Update and scan: Run a scan with Microsoft Defender and make sure Windows and your applications are up to date.
  5. Secure your accounts: If there are strong signs of compromise, use a trusted device to change affected passwords and enable multifactor authentication.

If this is a work or organization-owned computer, contact IT support or the security team before deleting evidence or making major changes.

Common mistakes when reading sign-in logs

  • Treating every 4624 event as proof that a person used the computer.
  • Ignoring Logon Type and looking only at the timestamp.
  • Confusing the account in Subject with the one in New Logon.
  • Assuming a missing source address is suspicious.
  • Assuming the absence of event 4801 means someone deliberately cleared the log.
  • Believing logon records alone can reveal every form of spying.

Frequently asked questions

How can I tell who last used my computer while I was away?

Start by searching for event 4624, then check the time, account, and Logon Type. Event 4801 may help identify when the screen was unlocked if its auditing is enabled, but these events cannot prove the actual identity of the person.

Does Event ID 4624 while I'm asleep mean my computer was hacked?

No. Windows may record it when a service starts or another legitimate session is created. Check the logon type and account before drawing conclusions.

Why can't I find event IDs 4800 or 4801?

The auditing policy for workstation locking and unlocking might not be enabled, or older logs may no longer be retained.

Does Event Viewer work on Windows 11 Home?

Yes. Event Viewer is available on Windows 11 Home, although management of some advanced security policies varies by Windows edition.

Does the PowerShell command reveal the password used to sign in?

No. The command here displays information about recorded events, not account passwords.

Conclusion

To check whether unusual logon sessions occurred on Windows 11, start with Event Viewer and the Security log. Review events 4624 and 4625, then examine Logon Type, the account, the time, and related events. A log entry is a clue that needs context and interpretation—not conclusive proof of a breach.
